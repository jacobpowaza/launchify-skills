# Cleanup Rules

**Launchify Cleanup Protocol — Canonical Reference**

---

## Cleanup Philosophy

Optimize for:
1. correctness
2. security
3. architectural clarity
4. maintainability
5. consistency
6. simplicity
7. performance where relevant
8. fewer unnecessary dependencies
9. fewer duplicate sources of truth
10. easier future agent and human development

Do NOT optimize for smallest line count. A larger clear implementation is preferable to a smaller opaque implementation.

---

## Cleanup Flow

### Phase 1: Understand Before Deleting

1. Understand the project structure, frameworks, and conventions
2. Determine what is production-relevant vs demo/fixture/example/test code
3. Build a mental model of the codebase architecture
4. Identify the canonical patterns used in the project

### Phase 2: Identify

Search for dead code, duplicate logic, unused components, unnecessary complexity, AI-generated debris, dependency issues, configuration issues, architectural inconsistencies, incomplete refactors, test issues, and documentation issues.

### Phase 3: Classify

Classify each finding as:
- `SAFE_TO_REMOVE` — can be deleted with high confidence
- `SAFE_TO_SIMPLIFY` — can be simplified without behavior change
- `REVIEW_REQUIRED` — needs human judgment
- `LIKELY_INTENTIONAL` — appears unused but may have runtime purpose
- `DO_NOT_TOUCH` — critical or infrastructure code that must not be changed

### Phase 4: Implement

Make changes incrementally. After each change:
1. Run tests
2. Run type checking
3. Run lint
4. Verify behavior is preserved

### Phase 5: Verify

Re-run cleanup analysis on modified areas to confirm findings are resolved.

---

## Dead Code Detection

Find:
- unused functions, classes, exports, variables, constants, types, interfaces
- unused hooks, utilities, API wrappers
- unused feature flags, routes, endpoints, RPC methods
- unused database models, schemas
- unused migrations where safely removable
- unreachable branches
- code after guaranteed returns or throws
- abandoned implementations
- stale fallback paths
- old compatibility code no longer required

Use call graphs, imports, exports, runtime registration, route registration, dependency injection, reflection, dynamic imports, configuration, generated code, plugin loading, framework conventions, and tests before classifying something as dead.

**Never assume "not imported statically" means unused.**

---

## Duplicate Logic Detection

Find logically equivalent or substantially overlapping implementations:
- multiple auth checks doing the same thing
- repeated API wrappers
- duplicate validators, schemas, serialization logic
- repeated utility functions, error handling, retry logic
- duplicate state machines, networking code
- duplicated UI components, copy-pasted hooks
- duplicate database queries
- multiple implementations of the same abstraction
- old and new implementations both remaining after a refactor

Determine which implementation should be canonical. Consolidate toward the implementation that is more correct, better tested, simpler, more secure, more widely used, or better aligned with current architecture.

Do not centralize unrelated code merely because it looks similar.

---

## Unused Components and Files

Find:
- unused React/Vue/Svelte/etc. components
- unused pages, layouts, CSS, assets, images, icons
- unused configuration, scripts
- unused tests for deleted behavior
- orphaned documentation
- unused fixtures, stale mocks
- abandoned prototypes
- obsolete generated artifacts committed by mistake

Validate runtime and framework discovery rules before removing them.

---

## Unnecessary Complexity

Identify code that is materially harder to understand or maintain than required:
- excessive abstraction
- abstraction around a single trivial use
- wrapper-on-wrapper architecture
- unnecessary indirection, factories, adapters, service layers
- trivial helper functions that obscure behavior
- deeply nested conditional logic, giant condition trees
- unnecessary state, duplicated state
- overly complicated state machines
- unnecessary async behavior, queues, caching, memoization
- excessive defensive code that cannot occur
- obsolete backwards-compatibility branches
- premature optimization
- overly generic systems used for one concrete case
- complicated configuration for fixed behavior
- unnecessary dependency injection
- excessive event emitters, unnecessary internal RPC
- unnecessarily fragmented or large files
- abstractions generated by AI without architectural justification

Simplify only where behavior remains clear and correct.

---

## AI-Generated Code Debris

Explicitly search for patterns commonly left by coding agents:
- multiple attempted fixes living side-by-side
- temporary fallback implementations
- comments describing already-completed migrations
- "temporary" logic that became permanent
- duplicate interfaces with slightly different names
- adapters for APIs that no longer exist
- defensive checks against impossible conditions
- error swallowing introduced to make tests pass
- TODO/FIXME/HACK comments that indicate unfinished work
- debugging code, console logging
- experimental feature toggles
- mock behavior in production paths
- fake placeholder implementations
- obsolete shims, compatibility hacks
- broad catch blocks hiding failures
- unnecessary retry loops
- unexplained sleeps or delays
- code added solely to work around previous broken code
- commented-out code
- stale feature branches represented inside runtime code
- old architecture remaining beside replacement architecture

For each such area, determine the original intent before modifying it.

---

## Dependency Cleanup

Inspect package and dependency manifests:
- unused dependencies and dev dependencies
- duplicate packages serving the same purpose
- obsolete packages
- unnecessary heavyweight libraries
- dependency wrappers that can be removed
- multiple versions caused by poor dependency declarations
- packages added during experiments but never removed
- vulnerable dependencies
- unmaintained dependencies
- dependencies with dangerous install scripts
- dependencies that introduce unnecessary native or runtime attack surface

Do not replace mature dependencies with hand-written code solely to reduce dependency count.

---

## Configuration Cleanup

Find:
- duplicated configuration
- obsolete environment variables
- environment variables no longer read
- configuration values that contradict each other
- stale feature flags
- obsolete build options, outdated aliases
- duplicate tsconfig/eslint/build config
- old CI jobs
- obsolete deployment configuration
- stale infrastructure resources
- unused cloud services
- duplicate queues, buckets, databases, or deployment targets
- environment-specific behavior that is undocumented

---

## Architecture Consistency

Identify places where the codebase accidentally implements multiple competing architectural patterns:
- two API client layers
- two state management systems
- old and new auth systems
- multiple logging systems, error formats, validation libraries
- inconsistent dependency injection
- multiple persistence abstractions
- competing event systems
- old and new routing mechanisms
- multiple feature-flag systems
- multiple deployment mechanisms
- multiple infrastructure definitions for the same resource

Determine the intended canonical architecture from current usage, documentation, tests, recent implementation, dependency graph, repository structure, deployment configuration, and operational ownership.

---

## Incomplete Refactors

Search for evidence of partially completed migrations:
- deprecated functions still called
- re-export compatibility files
- legacy, old, v1, temp, new, backup, deprecated implementations
- TODO migration comments
- two data models representing the same entity
- old environment variables
- compatibility conversion code
- stale APIs, unused migration adapters
- old infrastructure resources still deployed
- old CI/CD workflows still active
- old feature flags controlling removed behavior

Finish the migration where evidence clearly shows which architecture replaced the old one.

---

## Test Cleanup

Identify:
- tests for deleted behavior
- duplicate tests
- tests that only assert implementation details
- permanently skipped tests
- outdated snapshots
- flaky tests masked with retries
- tests that never run
- mock-only coverage that misses actual security or behavior
- obsolete fixtures
- missing regression tests for known vulnerabilities
- tests that pass only because security checks are disabled
- tests that do not reflect production configuration

Do NOT reduce meaningful coverage just to make the test suite smaller.

---

## Documentation Cleanup

Find documentation that contradicts actual implementation:
- setup instructions
- environment variables
- API documentation
- architecture descriptions
- security documentation
- commands
- obsolete features, removed modules
- deployment instructions
- incident-response instructions
- feature behavior
- supported integrations

Update documentation to reflect the final repository state.
